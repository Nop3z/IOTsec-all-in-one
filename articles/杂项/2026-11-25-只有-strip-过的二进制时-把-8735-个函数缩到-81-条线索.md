# 只有 strip 过的二进制时，怎么把 8735 个函数缩到 81 条线索

> 本文同步发布于看雪论坛，作者 SpiralRise。

## 一、起点：没有源码，也没有符号

拿到一个第三方固件、一个厂商提供的 .so、或者一份只有二进制没有源码的交付物时，常规的审计开场是这样的：

```
file libssl.so.1.0.0
# ELF 64-bit LSB shared object, x86-64, ..., stripped
```

stripped 意味着符号表被删掉了。函数名、变量名、源文件名、行号全部消失，剩下的只有机器码和地址。丢进反编译器，看到的是 FUN_00424d40、pAVar1->length 这种东西。

这时候工具是够用的：capa 识别能力特征，cwe_checker 找缺陷模式，Ghidra 反编译，Semgrep 扫伪代码，Joern 做数据流。问题不在工具有没有，而在于它们是五个互不相通的工具：

- 五种输出格式，五套字段命名；
- 每个工具都需要你手工圈定范围；
- 结果要靠人肉合并，整理一遍半天就过去了；
- 换一个样本，前面所有步骤再来一遍。

所以真正要解决的不是"分析能力"，是"把分析串起来"。

## 二、为什么不做并联，而做漏斗

最直觉的做法是：五个工具全量跑一遍，最后合并结果。我试过，跑不动，原因很具体：

- cwe_checker 会在几乎每个 ELF 上报告 CWE676（使用危险函数），这是提示不是缺陷，但数量足以淹没真实问题；
- Ghidra 全量反编译的代价和文件数量成正比。一个 libssl.so 就是八千多个函数，几十个文件全量反编译，时间以小时计；
- Joern 给所有函数建 CPG 会直接 OOM。它的内存占用和图规模强相关，全量建图在普通机器上不可行；
- 报告会变成垃圾场。几千条命中混在一起，等于没有结论。

于是整条流水线被设计成一条漏斗：每一步只处理上一步筛出来的东西。

步骤工具作用默认1cve-bin-tool按版本字符串查已知 CVE关2capa能力识别，逐文件扫描开3cwe_checkerCWE 缺陷，CWE676 单独归类开4Ghidra只反编译 capa/CWE 命中的文件开5Semgrep用本地规则初筛伪代码开6Joern对 Semgrep 选中的范围做 source-to-sink 复筛开7Semgrep + Bandit + njsscan扫目标目录里的脚本开8summarize汇总成一份《高风险点清单.md》开

第 1 步默认关闭，因为它需要联网更新 CVE 库；在离线环境里，版本比对可以后面手工补。

## 三、实现上的几个关键取舍

这一节是流水线真正花时间的地方，也是它和"写个脚本循环调用五个工具"的区别。

### 1. 统一中间结构

五个工具的输出没有一处是相同的：capa 按规则和函数组织，cwe_checker 按 CWE 和告警组织，Ghidra 导出的是伪代码文件和函数清单，Semgrep 是 findings 数组，Joern 输出的是 flow 路径。

如果每个下游都直接读上游的原始 JSON，那么任何一个工具升级格式，整条链就断了。所以流程里有一个中间层：每个工具的输出先被各自的解析脚本转成统一记录（文件、函数、行号、规则、描述、原始证据），后面的汇总只消费这一层。

好处很直接：报告生成逻辑不需要知道 capa 的 JSON 长什么样；换工具或者加工具，只需要多写一个解析器。

### 2. Ghidra 只反编译"有理由看的文件"

select_reverse_targets.py 做的事情很简单：读第 2、3 步的命中结果，把出现过的文件去重，作为 Ghidra 的输入清单。

这里有一个容易忽略的细节：如果 capa 和 cwe_checker 都没有命中任何文件，不能直接输出空结果，否则会遇到"这个样本什么都没查出来"的假象。所以这种情况下会回退到全量反编译，宁可慢，也不给错误结论。

### 3. Semgrep 的结果决定 Joern 的范围

scope_from_semgrep.py 负责把 Semgrep 命中的伪代码文件拷进 Joern 的工作目录。

这一步是整条链里最重要的一环，因为它定义了 Joern 的问题边界：

- Semgrep 回答的是**"这里有没有危险调用"**，它是模式匹配，看的是单点；
- Joern 回答的是**"外部输入能不能走到这个点"**，它需要建图、跑数据流。

先做单点筛选再做数据流，比反过来便宜一个数量级。代价是 Joern 只能看到被选中的范围，这一点在报告里写明了，避免读者误以为"没报就是没有"。

### 4. Joern 查询的过滤规则

taint_scan.sc 跑完之后，原始结果里有一批必须过滤掉的噪音：

- 单节点自环：source 和 sink 是同一个节点，没有实际路径；
- source 落在 sink 名单里：某些库函数既被当作输入来源，又被当作危险操作，会制造大量假路径。

过滤之后每一条 flow 都带上源文件、函数、行号和代码片段，报告里可以直接定位。

### 5. 断点续跑，是能用和不能用的区别

一次完整运行二十分钟以上，如果中间某一步失败就要从头再来，这个工具就没人会用。

所以每一步的产物按 01_cve、02_capa 一直到 07_script 分开存放，步骤状态单独记录。带来的能力是：

- 中途失败，重跑时已完成步骤直接跳过；
- 只想重跑汇总，用 --only 8；
- 改了 Semgrep 规则，只重跑 5 到 8 步；
- 想换参数全量重来，用 --force。

这个特性看起来不起眼，但它决定了这条流水线是"演示用"还是"能天天用"。

## 四、实测：一个 strip 过的 OpenSSL 1.0.1c

样本是一个 2012 年的 Ubuntu 包，里面的 libssl.so.1.0.0 实际版本号是 OpenSSL 1.0.1c，属于 Heartbleed 影响范围。

输入目录 88 个文件，4 核 / 16G 的机器，完整 8 步跑完用了 24 分 23 秒。

结果规模：

项目数值进入 Ghidra 的文件10反编译出的函数8735Joern 确认的可达路径33危险 sink81

报告里最值得看的是危险 sink 表的第 79 条：

```
// openssl.c:19359  FUN_00424d40
memcpy(local_60, pAVar1->data, (long)pAVar1->length);
```

这条为什么值得单独拿出来讲：

- 拷贝长度 pAVar1->length 直接来自结构体字段，不是常量、不是 sizeof；
- 这个结构体字段来自网络报文解析路径；
- memcpy 的目标是一个固定大小的栈缓冲区。

这就是典型的"长度来自外部输入、未做校验就参与内存拷贝"的形态。Heartbleed 的核心问题正是缺失对心跳包声明长度的边界检查，最终导致越界读取。

## 五、必须说清楚的边界

这里有一条线必须画明白，否则就是夸大：

这条流水线不能证明漏洞存在。

- 二进制被 strip 之后，函数只剩 FUN_xxxx，静态分析无法确认 FUN_00424d40 就是 tls1_process_heartbeat；
- memcpy 的形态吻合，不代表这条路径在真实协议交互中可达；
- 可达性、可利用性需要动态验证：起一个本地服务，用构造的报文实际打一遍。

那它有什么用？

它把"8735 个函数"变成"81 条危险调用"，再把其中最像问题的一条排到你能看见的位置。在真实项目里，这个动作省掉的是几天的初筛时间，不是最后那一步确认。

报告里因此把 CWE676 这类提示和真实缺陷分开列，也把"静态命中"和"已验证"用不同措辞区分——宁可报告看起来保守，也不给读者错误的安全感。

## 六、使用方式

整个流程打包在一个 Docker 镜像里，目标样本不会被运行：

```
docker pull ghcr.io/spiralrise/binary-audit-pipeline:1.1.0

python3 audit.py /path/to/firmware /path/to/out
```

宿主机脚本只负责挂载目录和传环境变量，所有分析都在容器里完成。离线环境可以自行 docker save 打包。

项目地址：https://github.com/SpiralRise/binary-audit-pipeline

## 七、小结

多工具串联这件事，难点不在"调通五个命令"，而在三件事：

- 范围：每一步只处理上一步筛出来的东西，否则跑不完；
- 格式：统一中间结构，否则改一个工具就断链；
- 可重跑：分目录、留状态，否则没人愿意在真实项目里用它。

如果你也在做固件审计、第三方组件审计，或者只是想知道一个来路不明的 .so 里有什么，欢迎试用并提 issue。工具本身的迭代方向也很明确：把 capa 和 cwe_checker 这两个逐文件串行的步骤并行化，这是目前最容易拿到的性能提升。
